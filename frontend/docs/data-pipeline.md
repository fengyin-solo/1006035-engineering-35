# 运营概览取数链路与迁移说明

本文回答四件事：数据链路经过哪些环节、谁喂谁；旧结构数据怎么迁、以哪份口径为准；
迁移如何保证可重复、可续跑；概览口径与各模块待办清单如何保证只有一份。

## 1. 链路现状（改造前）

```
modules.ts 模块元数据 ──┐
（字段/状态/动作/末态） │
                        ├─→ local-service.runAction：动作改 status/pending/abnormal
seed.ts 示例数据 ───────┤
                        ├─→ local-store（localStorage: airport-ground-ops:entries）
localStorage 已存数据 ──┘            │
                                     ├─→ listRows(key)   ──→ 各模块页面
                                     └─→ allRows()       ──→ loadOverview ──→ 运营概览
```

各环节的职责与现存问题：

| 环节 | 现状职责 | 现存问题 |
| --- | --- | --- |
| 模块元数据 `modules.ts` | 声明 18 个模块的字段、状态、动作、流转目标、指标 | 概览按它迭代，但页面又各自硬编码了一份字段/状态/动作 |
| 本地种子 `seed.ts` | 首次打开 / 重置某模块时的兜底数据 | 与已存数据合并的规则模糊：解析失败会整份回退到种子，表现为“回到示例数据” |
| 持久化层 `local-store.ts` | 读写 localStorage 的扁平结构 `{ 模块key: EntryRow[] }` | 无版本号、无结构校验；缺模块靠 `?? []` 兜底；JSON 解析失败直接覆盖写回种子 |
| 概览取数 `loadOverview` | 现算四张卡 + 按模块统计表 | 直接信任行上的 `pending`/`abnormal` 冗余标记；旧结构行缺标记就被漏算；统计依赖行结构 |
| 各模块页面 | 列表、筛选、动作流转 | 页面硬编码字段/状态/动作；指标卡恒为 0；没有待办清单入口 |

关键矛盾：**`pending` 既被存在行上，又由“状态是不是末态”决定**，是两份口径。
记录结构一旦变动（缺字段、缺标记、多模块、少模块），概览就掉格或漏数据。

## 2. 改造后的链路（谁喂谁）

```
modules.ts 模块元数据  ── 唯一的「模块清单 + 结构/流转规则」来源
   │（模块增删、状态增减在这里改一处）
   ▼
seed.ts 示例数据      ── 只负责「首次播种」和「用户显式重置」，不参与任何统计口径
   │
   ▼
local-store 持久化层  ── 带版本号的信封 + 迁移 + 规范化；唯一的数据出入口
   │   读：旧结构 → 迁移到当前结构 → 规范化（缺模块=空模块、坏行隔离）
   │   写：一律先规范化再落盘；dataVersion 自增，通知所有取数方
   ▼
selectors（moduleStats / pendingEntries）── 唯一的「待处理/异常/总量」口径
   │            （pending 由元数据末态推出，不读行上冗余标记）
   ├─→ loadOverview：四张卡 + 按模块统计表（只迭代元数据，缺模块记 0）
   └─→ ModuleTodos：各模块页面的待办清单（与概览读同一个 selector）
```

依赖方向单向向下：**元数据喂持久化层与取数口径，持久化层喂取数函数，取数函数喂页面**。
页面不自己判断业务、不硬编码模块清单；种子只在“首次/重置”时喂持久化层，概览永不直接碰种子。

### 2.1 结构定义

持久化信封（localStorage value）：

```jsonc
{
  "version": 1,
  "modules": { "flight": [ { "id": 1, "status": "...", "abnormal": false, "...": "..." } ] },
  "appliedMigrations": ["0001-baseline"]
}
```

- `version`：当前结构版本；未来结构再变时新增迁移，不改老迁移。
- `modules`：以模块 key 为槽位。**持久化层只保证“key 存在且是数组”，模块是否有效由取数侧对照元数据判断**。
- 行上不再持久化 `pending`：它是派生值，由 `status` 与元数据末态实时推出。
  （迁移会把老行上残留的 `pending` 字段清掉，避免日后有人误读旧口径。）
- `abnormal` 保留为持久化事实：它由“撤销/作废/拒绝/驳回……”这类负向动作打上，
  无法仅从状态反推（异常行也可能停在普通状态）。

### 2.2 口径裁决：以元数据规则 + 行上状态为准

旧结构迁入当前结构时，三类数据分别裁决：

1. **待处理（pending）——以模块元数据为准重新派生，不沿用行上旧标记。**
   规则：`status !== 元数据末态(statuses 最后一个)` 即为待处理。
   依据：动作流转本来就是“状态变了才重算 pending”，行上的布尔值只是缓存；
   元数据是当前唯一有效的流程定义。缓存与定义冲突时以定义为准，这也修掉了
   “结构一变就漏算”的根因。
2. **状态（status）与业务字段——以行上已有值为准，迁移不动。**
   这是用户的真实操作结果，迁移只补缺、不改值。
3. **异常（abnormal）——以行上已有标记为准；老行没有该标记时补 `false`。**
   异常是负向动作产生的事实标记，无法由状态安全反推，缺失按“非异常”处理。

其他裁决：

- **缺 id 的行**：按其在模块数组中的稳定槽位补 `100001 + 模块序号*1000 + 槽位` 的确定性 id。
  确定性保证重复迁移同一批数据不会每次造新 id、不会产生重复记录。
- **重复 id**：同一模块内仅保留第一条，丢弃后续重复行（第一条视为原始登记，后面的是脏副本）。
- **坏行（不是对象）**：丢弃，不拖垮整页。
- **未知 key（元数据里已删除的模块）**：数据保留在存储里不删，但概览/页面不统计、不展示。
  将来重新加回同 key 模块，数据自然重新出现。
- **缺模块（元数据有、存储没有）**：当作空模块，三项指标都是 0，页面不报错。

## 3. 迁移：可重复、可续跑、不覆盖改动

迁移定义为有序、纯函数式的步骤表，逐步登记进度：

- 信封里带 `appliedMigrations`（已完成迁移 id 列表）。启动时从第一个未完成的迁移继续，
  **中途断了重开就从失败的同一步接着走**。
- 每个迁移按模块逐个处理，**每处理完一个模块就落盘一次并登记该模块进度**；
  断在第 N 个模块，重开只重跑第 N 个，前 N-1 个不重复处理。
- `0001-baseline` 的每个模块处理都是**幂等**的：规范化只补缺（id/abnormal）、
  派生 pending 只依赖当前 status、去重以 id 为准。对已迁好的数据再跑一遍结果不变：
  不新增记录、不改写 status/业务字段/abnormal。
- 与旧版兼容：无版本号的旧扁平结构 `{key: rows}` 视为“版本 0”，从 `0001` 开始迁移。

损坏隔离：localStorage 里的 JSON 整体解析失败时，**不再用种子覆盖**，而是把损坏原文
备份到 `airport-ground-ops:quarantine:<时间戳>`，本次以空数据启动并完成初始化，
避免“换台机器/缓存异常 → 回到示例数据”。

## 4. 单一待处理口径

- `moduleStats(key)` 是唯一计算入口：返回 `{ total, pending, abnormal }`，
  pending 由元数据末态派生。
- 概览统计表的待处理、四张卡里的待处理，都由它汇总。
- 各模块页面的「待办清单」组件 `ModuleTodos` 调用 `pendingEntries(key)`，内部复用同一判断。
- 持久化层在每次写入后自增 `dataVersion`，概览与待办清单响应式自动刷新，
  动作处理完一条，待办数两处同时减一，且始终相等。

## 5. 验证

- `npm run typecheck` 类型检查；`npm run build` 生产构建；`npm run dev` 本地开发。
- `npm run migrate:check` 用内存假存储跑迁移用例：旧扁平结构升级、重复执行幂等、
  中途失败续跑、缺模块/坏模块/坏 JSON 不炸页、口径与元数据一致。
- 构建产物只含 `seed.ts` 这份随仓库发布的示例数据；任何 localStorage 运行数据
  都在浏览器侧，不进 `dist/`、不进仓库、不进镜像（`.dockerignore` 排除）。
